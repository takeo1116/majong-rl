# GAME_SPEC.md

この文書は、本プロジェクトにおける **ゲームエンジンの長期実装仕様** を定義する。  
日常の実験判断は [PROJECT.md](/home/takeo1116/Git/majong-rl/docs/PROJECT.md) を正とし、個別実験の条件と結果は `experiments/exp_xxx/runbook.md` / `report.md` を正とする。  
本書は、ゲームルールそのものではなく、**そのルールをどういうエンジン構造で実装・拡張するか** を扱う。

採用ルールは `GAME_RULE.md`、学習基盤側の長期仕様は `RL_SPEC.md` を参照する。

---

## 1. この文書の役割

この文書の用途は次の3つに限定する。

1. ゲームエンジン変更を伴う CQ の設計基準にする  
2. 現在実装済みのエンジン境界と、意図的に省略している部分を明確にする  
3. 将来のルール拡張を、今の実装と混同せず記録する  

この文書は「今の実験で何を比較するか」を決める文書ではない。  
その役割は `PROJECT.md` と各 runbook/report が担う。

---

## 2. 文書の読み方

本書では内容を次の2層に分ける。

- **現仕様**
  - 現在のコードベースで成立している実装仕様
  - レビュー時に、実装と矛盾していないか確認する対象
- **将来案**
  - 今後の拡張余地として保持したい構想
  - 現実装前提では読まない

仕様変更を伴う議論では、まず現仕様を優先し、将来案は必要なときだけ参照する。

## 4. 現在地の要約

2026-03-08 時点のゲームエンジンは、**Stage 1 の DiscardOnly 学習基盤を支える実装** として成立している。

現状の特徴:

- 対局進行・合法手列挙・精算・観測生成は実装済み
- Debug / Fast の2モードを持つ
- rotation eval、baseline 対戦、reward 出力、state copy 前提の運用ができる
- 一方で、実麻雀の完全ルールをまだ全面実装しているわけではない

したがって本書は、完全麻雀実装の仕様書というより、  
**今の学習基盤を壊さずに実麻雀へ近づけるための長期設計図** として維持する。

---

## 5. 設計原則

### 5.1 基本原則

- ルール定義とエンジン仕様を分離する
- 状態は値コピー可能にする
- 同一 seed + 同一 action 列から同一結果を得られるようにする
- Debug / Fast の結果はルール的に一致させる
- 学習側都合の構造とゲーム進行ロジックを混ぜすぎない

### 5.2 責務分離

ゲームエンジン側の責務:

- 対局進行
- 合法手列挙
- 和了 / 流局 / 終局判定
- 精算
- 観測生成
- reward policy の計算

学習基盤側の責務:

- feature 化
- model 推論
- self-play 保存
- learner / batch 集約

### 5.3 拡張時の原則

今後ルール拡張を行う場合も、次を維持する。

- state copyability
- deterministic replay
- Debug / Fast 一致
- RL 側 API の後方互換

## 6. 現仕様: 実行モード

### 6.1 Debug モード

- 整合性チェックを積極的に行う
- 詳細ログを許可する
- assert を活用してよい

### 6.2 Fast モード

- 高速自己対戦・評価用
- ログや重い検証を抑制可能
- ただしルール結果は Debug と一致しなければならない

### 6.3 運用上の原則

実験運用では Fast を主に使うが、  
バグ調査・CQ 追加時には Debug で再現可能であることを重視する。

---

## 7. 現仕様: 状態モデル

### 7.1 基本構造

少なくとも次の層を持つ。

- `PlayerState`
- `RoundState`
- `MatchState`
- `EnvironmentState`

### 7.2 値コピー性

`EnvironmentState` / `RoundState` / `MatchState` は、  
**値コピーで完全複製可能** であることを前提とする。

これには:

- 対局状態
- 点数
- 山・配牌・河・副露
- phase / 文脈
- RNG 状態

を含む。

### 7.3 RNG

- `reset(seed)` ごとに再初期化
- seed + action 列で再現可能
- 状態複製に RNG 状態を含める

---

## 8. 現仕様: 牌・副露・行動の表現

### 8.1 牌表現

現仕様では次の2系統を使い分ける。

- **136 枚実牌 ID**
- **34 種インデックス**

用途:

- 実際の局進行や牌の所在管理: 136 枚
- 集計・判定・学習補助: 34 種

### 8.2 赤牌

- 赤 5 は通常牌と別実牌 ID を持つ
- 34 種上は通常 5 と同一
- 赤ドラ判定は実牌 ID に依存

### 8.3 Action 表現

Action は整数 ID だけではなく、意味を持つ構造体として扱う。

最低限必要な要素:

- `ActionType`
- actor
- tile（必要な場合）
- target_player（必要な場合）
- meld_type（必要な場合）
- `riichi` フラグ

現仕様で重要な `ActionType`:

- `Discard`
- `TsumoWin`
- `Ron`
- `Chi`
- `Pon`
- `Daiminkan`
- `Kakan`
- `Ankan`
- `Skip`

### 8.4 打牌と立直

現仕様では立直は独立 action type ではなく、

- `Discard + riichi=true`

として表現する。

## 9. 現仕様: phase モデル

エンジンは phase machine として振る舞う。

代表的な phase:

- `StartMatch`
- `StartRound`
- `DrawPhase`
- `SelfActionPhase`
- `ResponsePhase`
- `ResolveResponsePhase`
- `ResolveWinPhase`
- `ResolveDrawPhase`
- `EndRound`
- `EndMatch`

### 9.1 SelfActionPhase

現在手番プレイヤーの自発行動を解決する。

現仕様で候補になりうるもの:

- 打牌
- 立直打牌
- 暗槓
- 加槓
- ツモ和了

### 9.2 ResponsePhase

他家打牌への応答を解決する。

現仕様で候補になりうるもの:

- ロン
- ポン
- 大明槓
- チー
- スキップ

### 9.3 応答解決順位

少なくとも次の優先順位を一貫して守る。

1. ロン
2. ポン / 大明槓
3. チー

複数ロンは成立可能とする。  
この点は統計・精算・ログに影響するため、単一勝者前提に潰さないことが重要である。

---

## 10. 現仕様: 合法手列挙

### 10.1 原則

- 候補漏れを許さない
- phase ごとに列挙責務を分ける
- RL / 探索で使える完全列挙を優先する

### 10.2 SelfActionPhase の合法手

状況に応じて:

- 打牌
- 立直打牌
- 暗槓
- 加槓
- ツモ和了

### 10.3 ResponsePhase の合法手

状況に応じて:

- ロン
- ポン
- 大明槓
- チー
- スキップ

### 10.4 自動処理との境界

エンジン自体は和了可能性を把握するが、  
学習環境ラッパー側では Stage 1 簡略化のため、自動処理する行動がある。

したがって、

- エンジン本体の合法手列挙
- Stage1Env での自動処理

は意図的に役割が異なる。

## 11. 現仕様: Stage 1 簡略化

現在の学習運用では、エンジン能力のうち次だけを主に使う。

- 学習対象は打牌のみ
- ロン / ツモは自動
- テンパイ時自動立直
- 副露は使わない

これは **エンジンが副露不能** なのではなく、  
**Stage 1 の学習環境が副露を使わない** だけである。

将来のルール拡張では、まずこの境界を崩さずに Stage を進める。

## 12. 現仕様: 精算

### 12.1 基本

精算は `GAME_RULE.md` に従う。  
少なくとも現運用で重要なのは次。

- ロン
- ツモ
- 通常流局
- リーチ棒
- 本場
- 供託

### 12.2 複数ロン

複数ロンは起こりうる前提で扱う。

原則:

- 複数勝者を潰さない
- 統計・ログ・精算は複数勝者を保持できる構造にする

### 12.3 流局

現仕様で重要:

- 通常流局
- 九種九牌

### 12.4 reward との関係

精算結果は reward policy の入力になる。  
つまり精算変更はゲーム仕様変更であると同時に、RL 側 reward 分布変更でもある。

そのため精算変更を伴う CQ は、`RL_SPEC.md` とセットで見る必要がある。

## 14. 現仕様: Observation

### 14.1 PartialObservation

通常エージェント向けの観測。

少なくとも:

- 自家手牌
- 自家副露
- 全員の河
- 全員の公開副露
- ドラ表示
- 点数
- 局情報
- 本場
- 供託
- phase

を含む。

### 14.2 FullObservation

デバッグ・学習補助・探索補助用の観測。

少なくとも:

- 全員の手牌
- 山順
- 王牌
- 裏ドラ候補
- 局進行に必要な完全情報

を含んでよい。

### 14.3 原則

- 内部状態そのものを通常エージェントへ渡さない
- Partial と Full を分離する
- 観測はモデル非依存表現であり、feature 化は RL 側で行う

## 15. 現仕様: RewardPolicy

エンジン側は reward policy の計算を提供する。

現仕様での mode:

- `PointDelta`
- `FinalRank`
- `Combined`

ただし RL の主系運用で実際に使っているのは `PointDelta`。

### 15.1 PointDelta

- 点数差分を返す
- 局中は 0 が多く、点数変化時に非ゼロになる

### 15.2 FinalRank

- 半荘終了時の順位報酬

### 15.3 Combined

- 上記の組合せ

### 15.4 エンジン側の責務

- reward の算出
- 零和性や整合性の保証

### 15.5 RL 側との責務分離

- scale の適用
- learner での GAE / return / advantage 化
- reward 分布の診断

は `RL_SPEC.md` 側で扱う。

## 17. 現仕様: 探索補助

エンジンは探索アルゴリズム本体を持つ必要はない。  
ただし探索補助機能は持てるようにする。

主な補助:

- 完全状態コピー
- determinization を支える補助 API
- 整合性チェック

### 17.1 determinization

- エンジン内部は完全情報状態
- determinization は原則探索側
- そのための補助 API は提供可能

### 17.2 グローバル状態禁止

- static な可変作業領域に依存しない
- 並列利用や state copy を妨げない

## 20. 現在の既知課題

今のゲームエンジン側で意識すべき中長期課題は次。

1. Stage 1 の簡略化と、将来の実麻雀近似との間にギャップがある  
2. reward と精算が RL 学習品質に直接影響する  
3. ルール拡張時に、state copy / determinism / debug-fast 一致を壊しやすい  

したがって、今後のルール追加は「実麻雀っぽさ」だけでなく、  
**学習基盤を壊さず段階的に近づけること** を重視する。
